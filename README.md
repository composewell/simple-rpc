# simple-rpc

Zero setup RPC for distributed deployment and orchestration.

## How it works

simple-rpc calls a function on another machine the same way you already
run a command there: over ssh, and with `sudo` or `su` to run it as
another user. There is no always-running RPC server, no port to open,
and no package to install or configuration to change on the machine.

The server is a command line executable. It is a Haskell program
consisting of a collection of plain Haskell functions called endpoints;
each endpoint works like an independent command. Think of the executable
as a collection of custom commands which can be executed on a machine to
perform any task.

The client is a Haskell program. It calls an endpoint on a machine just
like a local Haskell function, by running the server executable on that
machine over ssh. You can also run the server executable yourself, like
any other command.

The only thing a machine needs is a copy of the server executable, which
the client can copy over ssh using `installOnRemote`. Therefore, this is
a zero setup RPC.

The output of a call on one machine can be used seamlessly as the input
of a call on another, so a deployment or a configuration change that
spans several machines can be written as a simple Haskell program.

## Usage

**Step 1: define endpoints.** Export a function as an endpoint with
`rpcExport`. The argument and result types must have `ToJSON` and
`FromJSON` instances:

```haskell
module Module1 (printFromModule1) where

import Simple.RPC

raw_printFromModule1 :: Int -> String -> Bool -> IO (Int, String, Bool)
raw_printFromModule1 val1 val2 val3 = ...

$(rpcExport "raw_printFromModule1" "printFromModule1")
```

This defines `printFromModule1`, the endpoint named
`Module1.printFromModule1`.

**Step 2: generate the endpoint map.** `simple-rpc-generate` generates
the `RpcMap` module, which lists all the endpoints of a library. It
reads the Template Haskell dump files of the library, so the library
must be built with `ghc-options: -ddump-to-file -dth-dec-file`. The
configuration file gives the build directory of the library, its source
directories and the module to generate; see `generate/README.md`:

```
cabal build lib:example
cabal run simple-rpc-generate -- rpcConfig.json
```

**Step 3: build the server.** Add `RpcMap` to the `other-modules` of the
server executable and call `mainWith` in its `main`:

```haskell
import RpcMap (rpcMap)
import Simple.RPC (mainWith)

main :: IO ()
main = mainWith "0.1.1" rpcMap
```

The first argument of `mainWith` is the version of the executable. The
client checks it before each call.

**Step 4: call the endpoints.** The client imports the endpoint and
calls it with `runAt`:

```haskell
import Simple.RPC
import Module1 (printFromModule1)

main :: IO ()
main = do
    let remote = ("user@host", "22")
        exe = Executable "/opt/simple-rpc/example-server" "0.1.1"
    installOnRemote
        (Executable "./example-server" "0.1.1") remote (executablePath exe)
    r <- runAt (setRemote remote (defaultConfig exe)) printFromModule1
            22 "Test" True
    print r
```

## Example

See `example` for an example application. `example/app/RpcMap.hs` is
generated by `simple-rpc-generate` from `example/rpcConfig.json`:

```
cabal build lib:example
cd example && cabal run simple-rpc-generate -- rpcConfig.json
```

`distBuildDir` in `example/rpcConfig.json` contains the platform and the
GHC version (`x86_64-linux/ghc-9.10.3`); edit it to match yours.

## Prerequisites

The server executable is built on a build machine and installed on the
target machines. The target machines must have the same OS and
architecture as the build machine, and compatible versions of the shared
libraries that the executable links to, unless it is statically linked.
When the endpoints use Haskell libraries such as streamly-coreutils
instead of external programs, the target machines need no other packages
installed.

* The remote machine must be accessible via ssh for some user(s), for
  example, by adding the user's public key to the user's
  `$HOME/.ssh/authorized_keys` file.
* The login shell of the ssh user must be a POSIX shell.
* The shell startup files of the ssh user (e.g. `.bashrc`) must not print
  anything to stdout, otherwise the version check fails.
* The client runs ssh with `-o "StrictHostKeyChecking off"`, so it does
  not verify the host key of the remote machine.
* To avoid putting the user's private key on each machine, ssh agent
  forwarding can be used to forward the keys from one machine to another.
  The client does not enable it; set `ForwardAgent yes` in the ssh
  configuration for the hosts that need it.
* A user with passwordless `sudo` is needed on each remote machine for:
  * installing the rpc executable
  * running commands as an arbitrary user

  ssh runs without a terminal, so `sudo` cannot prompt for a password.
* An endpoint function must not read stdin; the server reads its input
  from stdin.

## Using the server as a command

The server executable can be used as a CLI command to invoke any
endpoint from the command line. The endpoint name is the argument, the
JSON array of the function arguments is read from stdin, and the result
is printed as JSON on the last line of stdout:

```
echo '[22, "Test", true]' | cabal run example-server -- "Module1.printFromModule1"
```

Running the executable without arguments prints its version.

## Distributed scripting in Haskell

Your client program is essentially a Haskell script to perform the
tasks. Only the functions that run on another machine need to be
endpoints; all other function calls are local. An endpoint running on
a remote machine can in turn call endpoints on other machines. For
remote to remote calls, the remote machine needs ssh access to the
other machines, e.g. via ssh agent forwarding. By using modular
functions as endpoints, you can orchestrate a distributed computing
task.
